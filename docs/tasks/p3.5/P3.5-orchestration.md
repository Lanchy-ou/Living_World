shared-file rules (§5), decision rules (§6.1, §6.2) and tools (§7) apply to
every card here. This file adds what is new after M12. Read the
[P3.5 plan](../../plans/p3.5-implementation-plan-v0.1.md) §4, §5, §7, §9 and
§10 before you plan a milestone.

## 3. Planning a milestone

Task cards for M13 to M15 do not exist yet (plan §5: they are written after
M11, per milestone). Plan each milestone as a task of its own:

1. **Planner thread.** Use `gpt-6.2-sol`, xhigh, on branch
   `task/P3.5-M1<n>-cards`. It writes `docs/tasks/p3.5/M1<n>-plan.md` in
   the shape of the [M12 plan](M12-plan.md), with:
   - decisions;
   - waves and their start conditions;
   - file ownership;
   - a table that maps **every** spec test the milestone owns to exactly one
     card;
   - the Round 3 halves M12 deferred: MF-18 and DL-20/DL-27 to M14, and
     EV-22 to M15 (M12 plan §5, D3);
   - the deferred P3 items that fall due (plan §10).

   It also writes one card per task from `docs/tasks/_template.md`. Name them
   by plan §8, for example `P3.5-MM-01` and branch
   `task/P3.5-MM-01-<slug>`. Use the system prefixes from plan §1.
2. **Which spec tests belong to which milestone.** Take the milestone column
   or the text of each spec. For example, evaluation §8 puts MM-16, MF-14 and
   DL-19 in M14. Starter-content CT tests not run in M12 go to M13 (M12 plan
   §4).
3. **Independent review.** A reviewer thread checks the plan and cards:
   - every owned test is mapped exactly once;
   - every card has disjoint writable files from the cards it runs beside;
   - no card edits a frozen spec, ADR or product document;
   - dependencies and waves follow the specs and plan §3.

   The same fix-until-pass loop applies (M12 runbook §3 step 4).
4. Merge the plan and cards through a PR, then run the cards with the M12
   runbook's per-card cycle.

## 4. Provisional Gate 3

For each milestone, write `docs/tasks/p3.5/M1<n>-gate3.md` and merge it
through a PR. It contains:

- the plan §4 "Done when" and "Owner checks" for the milestone, each with
  its evidence: links to tests, reports and run outputs, plus the commands
  that reproduce them;
- what is missing or partial, stated plainly;
- every §6.1 decision of the M12 runbook made in this milestone, and every
  §1 decision above;
- the status line: "Provisionally passed by the orchestrator on <date>;
  awaiting owner signature."

Provisional pass requires:

- every card is merged;
- CI is green on `main`;
- the "Done when" condition is shown by evidence, not just by the absence of
  failures.

If the condition is not met, fix it first. Work that depends on the
milestone does not start until it is met.

Milestone notes:

- **M12:** the equivalence report from P3.5-PR-07.
- **M13:**
  - each starter-pack mechanic shown by a scripted scenario;
  - the long rule-based run meets the time budget you set and record (plan
    §4: the P3 long proof stalled at tick 132).
- **M14:**
  - the live check and the live resident follow §5;
  - every context is traceable;
  - replay needs no model call;
  - the extension tests MM-16, MF-14 and DL-19 pass;
  - the analysis-mode evidence named in plan §4 is included.

## 5. Paid model calls

- **Cap.** CNY 20 in total for P3.5, every provider call included. Keep a
  ledger at `docs/tasks/p3.5/P3.5-spend-ledger.md`. Each row has: date, run,
  provider and model, calls, input and output tokens, the price source, and
  the cost in CNY. Compute cost from the recorded call records, at the
  provider's published price (record the source and date).
- **Before each paid run:**
  - project its cost from a measured per-call figure;
  - run it only if the projected total stays under the cap;
  - stop the run before the call that would cross the cap.
- **Fake model first.** Every path that will make paid calls first runs
  end to end with the fake model.
- **Provider.** Choose the provider and model by ADR 0007 D7 and ADR 0013
  Q7, then run the provider live check before any longer run.
- **Keys.** Read them from `.env` at run time.
  - Never print, log, commit or pass a key into a prompt or thread message.
  - Never commit `.env` or anything under `runs/`.
- **M14** asks for one live resident "over several game days". Size the run
  to the remaining budget after the live check. If the budget covers fewer
  days than the milestone needs, run what fits, then record the shortfall
  and the measured cost per resident-day in the Gate 3 package.
- **M15.** The paid acceptance matrix (5 residents × 7 days × 6 runs, about
  CNY 900 by plan §4.1) is far above the cap. Do not start it. Finish
  everything that needs no paid calls:
  - the evaluation pipeline and its tests;
  - the fake-model run of evaluation §7.3;
  - the cost estimate from the M14 measurement.

  Then stop for the owner.
