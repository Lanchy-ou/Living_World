## Findings

### B1 (blocking): the rule file layout deviates from starter content §1 without a record

Starter content §1 lists the pack files: `pack.toml`, `materials.toml`,
`archetypes.toml`, `rules.toml`, `instances.toml`, `unmatched.toml` and
`compat-codes.toml`. This pack adds `rule-templates.toml` and makes
`rules.toml` one whole placeholder (`rule = "${rules}"`). The binding code
reads the templates, adds the regrowth rule when `regrow_per_cycle > 0`, and
passes the result in. The reason is sound: §4.7 says to omit the regrowth
rule for zero growth, and the RR-01 loader has no other way to omit one rule.
But the deviation is not recorded, and the regrowth rule sits under a
`[regrowth]` table, so tools that read rule files do not see it as a rule.

Requested fix:

- Keep the approach. Put the regrowth rule under a `rule` section, either in
  its own file (for example `rule-regrowth.toml`) or as a one-row `[[rule]]`
  array, so every rule of the pack sits under a `rule` key.
- Add an entry to `docs/spec/open-questions.md`: the template files, why
  `rules.toml` is bound whole, and that the pack loads only through
  `load_compat_pack`.

### N1 (non-blocking, do now): pin the identity checks in tests

The effective hash and `P2_SEEDS` agree with v1 today, but no test pins
them. P3.5-PR-07 relies on both. Add a test that loads the production
config with one P2 seed and compares the manifest with the `source` of the
matching P3.5-PR-03 matrix fixture (config blob, effective config, map,
seed). Also assert that `P2_SEEDS` equals the set of seeds in those fixtures.

### N2 (non-blocking, optional): one check no caller can trigger

`load_compat_pack` checks `type(seed) is not int` although `seed` is typed
`int | None`. Under the AGENTS.md boundary rule this check can go; the
registered-seed check stays.
