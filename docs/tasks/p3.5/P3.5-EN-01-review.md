## Findings

### B1 (blocking): the initial snapshot hash depends on Python's hash seed

`initialize` hashes `asdict(state)`. Several state fields are `set[str]`:
`visible_entities_by_resident`, `entity_counter.issued`,
`Receipts.item_tiles`. `to_jsonable_python` turns a set into a list in set
iteration order, which for strings changes with each process
(`PYTHONHASHSEED`). Only `opaque_terrains` is sorted.

Today the string sets are empty at tick 0, so the tests pass. P3.5-EN-05
fills `build_deliveries`, which records sight at initialization. The
reviewer stubbed that seam to record each resident's visible entities and
ran the same initialization under three hash seeds: the
`world_initialized` payload carried three different `initial_snapshot_hash`
values. This breaks reproducibility (AGENTS.md principle 5), and P3.5-EN-07
will hash the same state.

Requested fix:

- Build the canonical form with every set sorted, in one helper that hashes
  engine state, so P3.5-EN-07 reuses it.
- Add a test that fails today: populate string sets and compare the hash
  computed in two subprocesses with different `PYTHONHASHSEED` values.

### B2 (blocking): initialization refusals without a test, and two checks no input reaches

The AGENTS.md boundary rule asks that each real check ships with a test
that reaches it, and that checks no input can trigger are removed.

Reachable but untested (RR-01 checks only the shape of these rows; the
resident list and map arrive with `WorldSetup`):

- `place_entities`: placement ID equal to a resident ID, tile not passable,
  unknown holder, unknown owner, non-portable entity with a holder,
  container that does not accept its content, declared `contents` that
  disagree with the placements, container over capacity, resident
  inventory over capacity.
- `EnginePack.from_pack`: pack without kernel timing, limits or
  `inventory_slots` (the plain `engine-test` pack reaches it).
- `WorldSetup`: duplicate pack ID, duplicate resident ID, resident on an
  impassable or out-of-map tile, duplicate or out-of-map cue;
  `ClockConfig` bounds.

Unreachable, remove:

- The placement container cycle check. A placed entity inside a container
  must be portable (checked just before), and a portable container never
  accepts a container (RR-01 validator, rule representation §3.1). A cycle
  would need a portable container that accepts a container, so no valid pack
  reaches it, and the `accepts` check would refuse it first.
- `complete_kernel` returning `DEAD` when the actor is not alive. Dead
  actors never enter the completion set (`action_progress` skips them), and
  deaths happen in phase 5, after completion.

Requested fix: one parametrized test of the reachable refusals (one row
each, asserting the message), and remove the two unreachable checks.

### N1 (owner decision): CR-P3.5-EN-01, footprint flags

The proposed CR asks whether `footprint.blocks_movement` and `opaque` set
to `true` are inert data or must be refused. The executor recommends
accepting them as inert, which changes the engine contract.

Reviewer's reading: the specs do not contradict each other. Rule
representation §3 gives the field types; engine §6 adds the v0.1 rule that
the loader refuses `true`. The merged RR-01 validator does not apply that
rule, and the CT-01 fixture `arch_f` sets `opaque = true`. The reviews of
P3.5-RR-01 and P3.5-CT-01 missed it.

Recommendation: keep the frozen rule and reject the CR. A small fix card
adds the refusal to the RR-01 validator with a negative fixture, and sets
`opaque = false` on `arch_f`, keeping the CT-14 coverage test green. A
silently ignored
`true` would let a pack author believe a wall blocks sight when it does
not. EN-01 does not read the flags, so this does not block EN-01.
