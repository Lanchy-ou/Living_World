## Findings

### B1 (blocking): the `world.v2` purity contract does not stop imports of v1 world modules

The contract "world.v2 imports no other living_island subpackage" forbids
`living_island.*`. Import-linter does not apply it to `living_island.world`,
the package that contains the source, so `world.v2` may import any v1 module
under `living_island.world`.

Reproduction: copy `backend/src/living_island` to a temporary directory, add
`world/v2/probe.py` containing
`from living_island.world.content import canonical_json_bytes`, and run
`lint-imports --no-cache` with this branch's `pyproject.toml`. All 12 contracts
are reported kept. The same import was present in the first P3.5-RR-01 draft
and passed this contract unnoticed.

Why it blocks: M12 plan decision D2 removes the v1 engine after M14 Gate 3, so
any `world.v2` dependency on v1 world code breaks then. The card asks that
`world.v2` be "pure like `world`", and the M12 plan (D1) says the import-linter
purity of `world` extends to `world/v2`.

Requested fix:

- Add a contract that refuses imports from `living_island.world.v2` (all
  descendants) to every v1 module under `living_island.world`, for example by
  listing the v1 modules explicitly as forbidden modules.
- Extend `test_import_boundaries.py` with the probe above: a new `world/v2`
  module importing `living_island.world.content` must break that contract.

### N1 (non-blocking): `schema_version` on every DTO

Protocol §1 says every v2 DTO carries `schema_version`, while the shapes of
`BoundaryDelivery` (§5.3) and `ActionResult` (§4.1) do not list it. The
implementation follows the shapes (`TurnSubmission`, `Perception` and the
event envelope carry it; `BoundaryDelivery` carries it inside its
`Perception`). No change requested; record it as a note for the next
protocol change request.

### N2 (non-blocking, not this card): Hypothesis deadline
