# Task P2-F0: Frontend design spec (documentation only, before P2-04)

## Brief

```text
Task ID / title: P2-F0 — Frontend design spec, style samples and asset interface
Spec baseline (commit SHA): main @ 821cd88 (P2-00..P2-03 merged; plan Amendment 1)
Goal / non-goals:
  Goal: P2 plan §2 P2-F0 (PD-08, Amendment 1). Write the design that P2-F1 implements on
  the existing replay viewer:
  - the visual direction;
  - the asset interface (product document §9.2);
  - layout and interaction;
  - the change set against docs/spec/p1-replay-frontend-v0.1.md;
  - acceptance checks.
  Give the owner concrete style options to choose from at MF.
  Non-goals:
  - any code in frontend/ or backend/;
  - any change to contract/, generated files, ReplayBundle or DisplayFrame;
  - features that need data the replay does not carry, for example personality, goals,
    memory, perception overlays, relationships, LLM traces, god controls, live view or
    narrative (P3 and later per product document §9.1);
  - final art production. Samples are enough to choose a style.
Lane / depends on: after P2-03 and plan Amendment 1. The only active task, so a reviewer
  can take the second slot.
Allowed files / forbidden dependencies:
  docs/spec/frontend-design-v0.1.md (new; the design spec);
  docs/adr/0005-frontend-rendering.md (new, only if a rendering approach is chosen; status
    Proposed until MF);
  docs/design/** (new: style samples, mockups and asset-pipeline notes);
  docs/tasks/p2/P2-F0.md; docs/spec/open-questions.md (append only, after OQ-078).
  Mockups are static images, or self-contained HTML files under docs/design/ that load no
  network resources. They are not imported by frontend/ and are not part of the build.
  Forbidden: frontend/**, backend/**, content/**, scripts/**, contract and generated
  files, every other spec, ADR and plan, CI.
  Third-party assets: none is committed or downloaded without the owner's approval in
  chat. A proposed third-party asset is listed with its source, license and author, and
  must allow redistribution in this repository. Generated or hand-made samples need no
  approval but record how they were made.
Deliverables:
  1. Visual direction: two or three distinct style options (for example pixel art, flat
     vector, simple illustration). Each option has:
     - one map mockup at the default 64x64 island scale, showing every terrain type, a
       tree with stock, ground fruit, the ground canteen, a corpse, three residents
       (one sharing a tile) and night shading;
     - one close-up of a resident with the side panel;
     - a short note on cost, readability and the risk of rework if M6 changes the map.
     State a recommendation.
  2. Asset interface:
     - tile pixel size and the scaling rule for fit and zoom (the existing ×1/×2/×4 camera
       stays unless the spec changes it);
     - layer order, for example terrain, ground items, trees, corpses, residents, effects,
       night overlay and selection;
     - resident facing and animation conventions. Facing and motion are display-only and
       derived from recorded positions in consecutive frames. If a convention needs data
       the replay does not have, drop it or raise an OQ;
     - naming, file layout and formats under the frontend asset path P2-F1 will use;
     - the license and source record format.
  3. Layout and interaction: the map, time controls, resident, resource and event panels
     and the debug view. Base it on p1-replay-frontend §4 and state each change. Keep
     accessibility rules: colour is never the only cue, and residents have colour plus a
     letter or another non-colour mark.
  4. Data mapping: a table from every displayed element to the existing ReplayBundle /
     DisplayFrame / event field it reads, with file and line on 821cd88. An element with no
     field is removed or becomes an OQ for a later phase. Any derived display value
     (facing, interpolation, night shading) is a pure function of recorded frames and is
     never written back or used as a world fact.
  5. Change set against p1-replay-frontend-v0.1.md:
     - FE-01..FE-04, especially FE-04 "Simple 2D Canvas";
     - §4 features;
     - §6 technical constraints, including any new dependency such as PixiJS, with its
       version, license and bundle-size impact;
     - which FE-T01..FE-T13 tests still apply unchanged.
     The P1 spec file itself is not edited; the new spec states what it supersedes.
  6. Acceptance checks for P2-F1, as a numbered table like FE-T. Include at least:
     - every FE-T that still applies;
     - every layer drawn in order;
     - the shared-tile and corpse cases;
     - zoom and pan keep entities on their recorded tiles;
     - a 1,009-frame rule-based default-island replay plays at 16 ticks per second;
     - the P1 replay fixtures still load;
     - no game logic in the frontend;
     - the asset license record is complete.
Acceptance (positive, negative, edge, determinism):
  - Every displayed element maps to an existing contract field or is a stated pure display
    derivation of recorded frames.
  - Nothing in the design computes legality, physiology, resources or outcomes (AGENTS.md
    principle 6; p1-replay-frontend FE-03).
  - Each style option covers every element listed in deliverable 1, and each mockup states
    its tile size.
  - The asset interface is complete enough that P2-F1 can add an asset without a design
    decision.
  - Every change to the P1 frontend spec is listed. Unchanged parts are stated as kept.
  - Every third-party asset reference has source, license and author, and none is committed
    without the owner's approval.
  - No file outside the allowed list changes.
Verification commands: no code changes, so the backend and frontend checks are expected
  unchanged. Run pnpm --dir frontend lint, typecheck and build, and
  git diff --name-only origin/main...HEAD, to show that nothing outside the allowed files
  changed. Open every HTML mockup offline to confirm it loads no network resource. Mark
  anything not run as NOT_RUN with the reason.
Open risks / deferred decisions:
  - The style choice is the owner's at MF. The executor recommends but does not decide.
  - A rendering-library choice that adds a dependency is recorded in ADR 0005 and needs
    MF approval.
  - Data gaps found while designing become OQs for P3 or later. Do not propose contract
    changes in P2.
  - If M6 changes the map, the design must still work. Show this by keeping all map drawing
    data-driven.
```
